# Data Quality Pipeline for BI Reporting

A Python pipeline that takes raw exports from a source system (domain: import supply chain), cleans and normalizes them, models them as a BI-ready star schema, and runs a **two-layer data-quality audit** based on the **DAMA-DMBOK** framework. Gates stop a broken dataset before it reaches the dashboard.

> **Portfolio demo.** The business domain is fictional and all data is **100% synthetic, generated by code**. It does not represent any company, client or real data.

**Status:** complete demo · 24 passing tests · Python 3.10+

## The problem

Data feeding a dashboard rarely arrives clean. A typical ERP export brings:

- dates in **mixed formats** (`2026-06-19`, `19/06/2026`, `19-06-2026`),
- numbers in **US format** with thousands separators (`12,345.67`) next to European format (`12345,67`),
- **missing values** encoded many ways (`""`, `N/D`, `-`),
- **duplicates** from source-system resends,
- **headers that change** between exports,
- text with **inconsistent casing and spacing**.

Publishing that straight to Power BI produces wrong metrics and broken refreshes. This pipeline puts a **clean → validate → audit** stage between raw data and the analytical model, with **gates that keep a corrupted dataset away from the dashboard**.

## Run it

Requires **Python 3.10+**. Works right after cloning; config has defaults and `.env` is optional.

```bash
git clone https://github.com/Darkslidex/pipeline-bi-calidad-datos.git
cd pipeline-bi-calidad-datos

python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env               # optional: thresholds and paths

python -m src.generar_datos        # 1. synthetic raw exports  → data/inbox/
python -m src.limpiar_datos        # 2. cleaning pipeline      → data/processed/
python -m src.auditoria_calidad    # 3. DAMA audit             → verdict + JSON
pytest -q                          # 4. tests
```

### What you'll see

- The **cleaner** ends with `exit 1 (WARNING)` on a normal run: it publishes the data but reports removed duplicates and quarantined rows.
- The **audit** prints the score per dimension and the overall verdict (`SALUDABLE` / healthy on a sound run).

To see the **gates in action**: delete a canonical column from a raw export and rerun the cleaner. It ends with `exit 2 (SCHEMA)` and **publishes nothing** to `processed/`.

## The 6 DAMA dimensions

The Layer 2 audit applies 12 rules across the DAMA-DMBOK quality dimensions:

| Dimension | Question | Rules |
|---|---|---|
| **Completeness** | Are key fields present? | `id_proveedor` and `fecha_despacho` coverage |
| **Validity** | Do values fall in valid domains and ranges? | statuses in domain, positive amounts, non-negative amounts |
| **Reasonability** | Is the value plausible for the business? | delivery lead time in range, `amount = quantity × price` |
| **Uniqueness** | Are there duplicates by key? | order uniqueness, supplier uniqueness |
| **Consistency** | Are tables referentially coherent? | FK order→supplier, FK transit→order |
| **Currency** | Is the data fresh? | age of the most recent record |

Each rule returns `PASS` / `FAIL` / `SKIP`. The dimension score is the weighted share of passing rules (`SKIP` does not penalize). The verdict comes from configurable bands (`HEALTHY ≥ 90`, `DRIFT ≥ 75`, `CRITICAL < 75`) and is **downgraded to DRIFT** if the score drops versus `baseline.json` by more than the configured tolerance.

## Design decisions

### Why a star schema?
Separating **facts** (measurable events: orders, shipments) from **dimensions** (context: supplier, country, time) is the standard BI pattern. It speeds up aggregations and filters, lets Power BI or Looker build `1:*` dimension→fact relationships without costly joins, and keeps a dedicated `dim_calendario` for time intelligence (YTD, quarters, seasonality).

### Why delta and full load modes?
- **full** (replace) for entities the source exports complete every time: the supplier catalog and accumulated transit. Simple and always consistent with the source.
- **delta** (append, newest wins by key) for incremental facts such as orders: history is kept without reprocessing, and a corrected resend **updates** the existing row instead of duplicating it (idempotent, supports retroactive fixes).

### Why distinct exit codes?
A plain pass/fail is not enough for an orchestrator:

| Code | Meaning | Publishes? | Upstream action |
|---|---|---|---|
| `0` OK | clean run | yes | refresh BI |
| `1` WARNING | published with notes | yes | refresh BI + log warning |
| `2` SCHEMA | a canonical column is missing | **no** | **stop refresh** + alert |
| `3` ERROR | unhandled failure | **no** | **stop refresh** + alert |

The exit code becomes an **operational contract**: the job that triggers the dashboard refresh only proceeds on `0` or `1`.

### Why a two-layer audit?
They answer different questions, at different times, for different audiences:

- **Layer 1, per-run integrity** (inside the cleaner): *"Did today's run finish correctly and do the numbers add up?"* Operational and automatic; checks counts, duplicates, control sums and schema.
- **Layer 2, DAMA audit** (separate script): *"Is the published dataset defensible for analysis?"* Analytical and periodic; measures quality against business rules and a baseline, and issues a verdict you can communicate.

Mixing them hides signal: a pipeline can run perfectly (Layer 1 green) and still publish data that drifted from its baseline (Layer 2 in DRIFT).

## Security notes

- **Data is never versioned.** `.gitignore` excludes `data/`, snapshots, reports and any `.csv`/`.xlsx`. The repo holds code, not data.
- **Config separate from code.** Parameters live in `.env` (not versioned); the repo only ships `.env.example` with placeholders, never secrets. In a real deployment `.env` is protected with `600` permissions.
- **Input validation as a barrier.** All external data passes through **Pydantic** models before being written; a row that breaks the contract goes to `quarantine/`.
- **Gates that stop downstream.** Exit codes `2`/`3` keep a corrupted or incomplete dataset away from reporting.
- **Synthetic data.** No personal or sensitive information; everything is generated by code from a reproducible seed.

## Tests

24 tests (pytest) cover number and date normalization across mixed formats, status normalization, composite-key deduplication, column-contract detection, header aliases, delta vs. full load modes, row-level quarantine, dimension scoring, verdict bands, baseline drift and the duplicate-key rule.

## Limitations

- The source system is simulated; there is no connector to a real ERP.
- No orchestrator or Power BI file is included: the exit codes and output tables are the integration contract.
- Code identifiers, console output and comments are in Spanish.
